# AI Delivery Impact: Implementation Prerequisites

This document tracks the organizational and repository setup required before the `ai-delivery-impact` skill can produce trustworthy reporting. The skill interprets evidence; these prerequisites create and retain that evidence.

## Desired outcome

For a declared set of repositories and reporting periods, compare AI-assisted, explicitly non-AI, and unknown-attribution delivery using PR flow, work mix, and release outcomes. Preserve attribution confidence and avoid treating missing evidence as proof that AI was not used.

## Measurement philosophy: why these metrics

The goal is to understand whether AI usage helps the team deliver useful work more effectively. It is not to maximize AI activity, count generated code, or create a developer productivity score.

Use a small set of understandable outcome and flow measures before adding new metrics:

- Start with the PR timing metrics already generated by the organization: time to first response and time to close.
- Treat revisions, review churn, and similar intermediate activity as mechanisms that may affect delivery time. Do not score the activity itself when its impact is already visible in time to close or release cadence.
- Exclude merge rate from the initial scorecard. Closing unnecessary or obsolete work can be healthy, so a higher merge percentage is not automatically better.
- Treat release count and release frequency as team-level delivery-health signals rather than attempting to attribute every release to an individual PR.
- Interpret release frequency alongside the mix of work being delivered. Frequent dependency or maintenance releases provide different context from frequent feature, defect, security, or infrastructure releases.
- Use AI attribution and work type as dimensions for interpreting delivery metrics, not as goals by themselves.
- Prefer metrics that can be explained plainly and audited from GitHub evidence.
- Avoid a single composite effectiveness score. Show the underlying measures and trends.

The central question is: **Is the team using AI to deliver an appropriate mix of work with faster or healthier flow, without hiding weak evidence behind an arbitrary utilization score?**

## Current foundation

The `RedVentures/compass-voice-api` repository already runs a weekly workflow at `.github/workflows/pr-metrics.yml` that calls:

```yaml
RedVentures/ai-products-gha/.github/workflows/pr-metrics.yml@v1.7.0
```

Current behavior:

- Uses `github-community-projects/issue-metrics@v3`.
- Selects PRs by creation date (`mode: created`).
- Creates a weekly GitHub issue, such as [compass-voice-api#502](https://github.com/RedVentures/compass-voice-api/issues/502).
- Also publishes repository snapshots and per-PR events to New Relic, but the skill does not depend on those events.
- Publishes time to first response, time to close, time to answer, comment count, status, and draft time when available.
- Excludes a fixed list of dependency and automation bot authors from the search query.

The existing workflow and generated GitHub issue are sufficient for the initial reporting architecture. No New Relic schema change or additional ingestion workflow is required.

## Canonical metric sources

Reuse the organization's generated metrics rather than reconstructing the same measures from GitHub timelines.

| Data | Canonical source | Direct GitHub use |
| --- | --- | --- |
| Time to first response, time to close, comment count, weekly intake counts | Row-level values in the generated weekly metrics issue | Do not recalculate or backfill missing values |
| AI authoring attribution and work type | Standardized PR labels and structured provenance | Read labels, description declarations, registered assistant identities, and controlled branch conventions |
| AI review activity | Registered reviewer/check identities | Read reviews, comments, and checks without treating review-only activity as AI authoring |
| Snapshot open and closed status | Generated weekly metrics issue | Preserve the point-in-time snapshot |
| Current outcome state | GitHub PR record | Report separately for issue-listed PRs; do not use it to revise or backfill timing metrics |
| Development and production releases | GitHub Releases | Read `.rc` prereleases and full releases |

### Required discovery sequence

Before calculating any flow metric:

1. Search each repository for issues titled `Weekly PR metrics report (YYYY-MM-DD..YYYY-MM-DD)` created by GitHub Actions.
2. Select generated reports whose date windows cover the requested period.
3. Parse the per-PR table, retain the report URL and reporting window, and deduplicate by repository plus PR number.
4. Use the weekly aggregate row only for that exact weekly window. For multi-week analysis, calculate statistics from the generated per-PR values; never average weekly medians or percentiles.
5. Build an exact PR lookup allowlist from the PR URLs in those issue rows, then batch-query GitHub for only those PRs' number, labels, author, branch, current state, and URL.
6. Resolve complete labels immediately. Fetch descriptions, contributors, commits, reviews, or other deeper evidence only for unlabeled, incomplete, or conflicting PRs.
7. Do not search for additional PRs by merge date, author, branch, repository activity, or any other route. Query GitHub Releases separately for development and production release cadence.

If a requested partial week has not produced a report, mark the period as pending. Independently calculate a flow metric only after telling the user that the canonical source lacks coverage.

### Snapshot limitation that must remain visible

The weekly issue is generated after the intake week and is not updated when an initially open PR later closes. For example, [compass-voice-api#502](https://github.com/RedVentures/compass-voice-api/issues/502) records PR #501 as open with no close time even though the PR subsequently merged.

Retain that missing duration and snapshot status exactly as generated. Do not fetch current lifecycle timestamps to backfill or revise the record. Because the workflow uses `mode: created`, that PR will not appear in the following week's created cohort merely because it later closed. Missing close times are therefore censored observations and may systematically underrepresent longer-lived PRs; disclose the count with every close-time statistic.

### Source ledger required in every report

Record, at minimum:

- Repository and generated report URL
- Covered date window and cohort type
- Number of parsed per-PR rows
- Missing or pending weekly windows
- Metrics read from the generated issue
- Classification fields added by the batched GitHub query
- Deeper fallback evidence fetched for incomplete attribution

Jira and third-party engineering dashboards are outside the initial architecture. The GitHub-native report must remain complete without them.

## 1. Establish repository scope

- [ ] Decide how repositories enter the program: explicit allowlist, GitHub team ownership, organization topic, or organization-wide with exclusions.
- [ ] Record repository status such as active, archived, experiment, generated, or production.
- [ ] Define the team responsible for each repository during each reporting period.
- [ ] Decide whether forked repositories and repositories without deployments are included.
- [ ] Roll out or verify the centralized metrics caller in every in-scope repository.

An explicit allowlist is the safest initial scope. It avoids mixing production services with templates, experiments, and inactive repositories.

## 2. Add AI provenance labels

Create these labels consistently in every in-scope repository:

- `ai-assisted`
- `no-ai-assistance`
- `ai-tool:<slug>`, with one label for every materially contributing assistant

Examples include `ai-tool:codex`, `ai-tool:claude`, `ai-tool:cursor`, `ai-tool:devin`, and `ai-tool:windsurf`. New assistants must be accepted without changing the data model.

- [ ] Add the labeling requirements to the root `AGENTS.md` in every repository.
- [ ] Define “material contribution” once for the organization.
- [ ] Require exactly one of `ai-assisted` or `no-ai-assistance`; no label means unknown attribution.
- [ ] Permit multiple `ai-tool:*` labels on a PR.
- [ ] Define the fallback PR-description declaration for agents without label permissions.
- [ ] Create an organization-maintained registry of known assistant bot identities, task-link formats, and controlled branch prefixes.
- [ ] Decide how labeling errors and conflicting evidence are reviewed.

The labels are the source of record. Description text, known bot contributors, task links, branch names, and titles are fallback evidence only.

## 2a. Add type labels

Use `AGENTS.md` to require one primary type label on every PR. This supplies context for what the team is delivering and prevents release or PR volume from being interpreted without regard to the work mix. The shorter `type:` namespace is sufficient for automation; `work-type:` is unnecessary.

Recommended initial taxonomy:

- `type:feature`
- `type:bugfix`
- `type:maintenance`
- `type:dependency`
- `type:infrastructure`
- `type:security`
- `type:documentation`

- [ ] Select and document the final organization-wide taxonomy.
- [ ] Require exactly one primary `type:*` label per PR unless there is a demonstrated need for multiple labels.
- [ ] Add type-labeling requirements to the root `AGENTS.md` in every repository.
- [ ] Define a fallback for PRs that cannot be classified automatically.
- [ ] Include the type label in the batched GitHub enrichment and weekly report.

Type labels allow the team view to answer questions such as whether AI assistance is concentrated in maintenance work, whether feature delivery is increasing, or whether faster close times merely reflect a shift toward smaller dependency updates.

## 3. Fix the PR cohort boundary

The current `mode: created` issue answers, “What happened to PRs opened during this week?” Its PR rows are also the complete and exclusive PR lookup scope for the report.

Within that issue-listed cohort, preserve two views:

1. **Intake view:** every PR listed in the generated issue, using its generated response and close metrics.
2. **Outcome context:** those same PRs segmented by current GitHub state, reported separately from the generated snapshot.

Do not search for PRs that merged during the period but were created outside the selected weekly issues. Consequently, the current outcome view is not a complete inventory of everything merged during the period; state that limitation plainly. Release activity remains a separate repository-level delivery signal.

- [ ] Use the generated issue rows as the exact PR allowlist.
- [ ] Preserve the generated issue's point-in-time open and closed status and keep it separate from current GitHub state.
- [ ] Preserve open and draft PRs as censored observations rather than assigning them a completed duration.
- [ ] Disclose that PRs created outside the selected issue windows are outside scope even if they merged during the reporting period.

## 4. Define the flow metrics precisely

| Metric | Recommended definition | Notes |
| --- | --- | --- |
| Time to first response | PR creation to earliest qualifying non-author, non-bot comment or submitted review, using the existing issue-metrics definition | Keep the current organization metric so teams can understand it consistently. If draft behavior materially distorts it, revisit the starting timestamp later. |
| Time to close | PR creation to closed timestamp, using the existing issue-metrics definition | Use as the main PR cycle-time measure. Preserve final status so merged and closed-without-merge work can be described separately without introducing a new merge-rate score. |
| Number of comments per PR | Existing issue-metrics comment count | Retain as descriptive context only. Do not treat more or fewer comments as inherently better. |
| Open, closed, and total items | Existing issue-metrics counts | Use to explain the weekly workload and incomplete observations. |
| Time to answer | Discussion creation to chosen answer | Not a PR metric; hide or ignore it for PR-only reporting. |

Use wall-clock duration initially. If business-hours duration is later required, document calendars, time zones, holidays, and team ownership before calculating it.

Do not add first-review, time-to-merge, review-iteration, changes-requested, or reversion metrics to the initial scorecard. If revision churn is slowing delivery, its effect should appear in time to close and release flow. Add a direct churn metric only if a later decision cannot be made from those outcome measures.

## 5. Implement report-time GitHub enrichment

Keep collection read-only and avoid a new ingestion pipeline.

- [ ] Parse PR URLs and numbers from each generated metrics issue.
- [ ] Treat the parsed repository-plus-PR-number set as an exact lookup allowlist.
- [ ] Batch-query lightweight PR metadata only for that cohort: labels, author, head branch, current state, and URL.
- [ ] Reject or flag any enrichment result not traceable to a selected issue row.
- [ ] Resolve AI and work type from labels without deeper calls when the declaration is complete.
- [ ] Fetch the PR description, contributors, commit trailers, task links, reviews, or checks only when primary labels are absent, incomplete, or conflicting.
- [ ] Record attribution confidence and the evidence source used.
- [ ] Preserve missing generated durations as censored; never backfill them from current GitHub state or timestamps.
- [ ] Read GitHub Releases once per repository and reporting period.
- [ ] Cache or deduplicate by repository and PR number within the run.

Use GraphQL pagination or an equivalent batch endpoint so enrichment is a small number of repository-level requests, not one request per PR.

## 6. Handle bots deliberately

The current search query excludes several dependency and automation accounts, while issue #502 still contains a `claude[bot]` PR. A single global “exclude bots” rule would remove legitimate AI-delivered work.

- [ ] Maintain separate registries for dependency bots, workflow bots, and AI assistants.
- [ ] Exclude dependency and workflow bots from human-review response calculations where appropriate.
- [ ] Retain AI-assistant-authored PRs in the issue-listed cohort.
- [ ] Ignore bot reviews and bot comments when measuring the first human response.
- [ ] Report automation-only maintenance separately if it would distort feature and defect work.

## 7. Establish comparison guardrails

- [ ] Report medians and 90th percentiles with counts; do not rely on averages alone.
- [ ] Suppress or clearly flag very small cohorts. Issue #502 contains only four PRs, which is too small for a stable weekly comparison.
- [ ] Compare within the same repository, work class, and time period when possible.
- [ ] Keep confirmed, probable, possible, and unknown attribution visible.
- [ ] Do not treat unknown attribution as non-AI.
- [ ] Do not rank individual engineers.
- [ ] Separate features, defects, maintenance, documentation, and automated dependency work when the data supports it.
- [ ] Publish the exact denominator next to every rate.
- [ ] Do not include merge rate, revision count, or reversion rate in the initial scorecard.

## 8. Track release health

Release activity provides a separate, team-level view of how regularly completed work reaches shared environments. It does not need to be mapped back to individual PRs for the initial report.

- [ ] Inventory which in-scope repositories publish GitHub Releases.
- [ ] Record release repository, tag, publication timestamp, draft flag, and prerelease flag.
- [ ] Classify `.rc` releases as development releases.
- [ ] Classify full, non-`.rc` releases as production releases.
- [ ] Count development and production releases separately by week.
- [ ] Calculate release frequency and the time between production releases by repository and across the team.
- [ ] Optionally calculate promotion time from an `.rc` series to its corresponding full release when version naming permits a reliable match.
- [ ] Preserve repositories that do not publish releases as a separate coverage category rather than treating them as zero-performing repositories.

### Why release frequency matters

More frequent releases generally indicate that the team can move completed work through its delivery system in smaller, regular increments. Interpret the signal with type mix and repository coverage:

- A high count of `.rc` releases shows active movement into development environments.
- A high count of full releases shows regular production delivery.
- A long gap between `.rc` and full releases may indicate slow promotion or stabilization.
- Release volume without type context can be misleading; dependency automation and feature delivery represent different kinds of output.
- Release frequency is a team-health indicator, not an individual productivity measure.

Do not assume that more releases always means better outcomes. Use the measure as trend and context alongside PR flow, work mix, failures, and incidents when those signals become available.

## 9. Add quality and outcome signals only when needed

Possible later signals include:

- Reverted PR or rollback deployment
- Corrective PR linked to the original change
- Incident linked to a deployment or change
- Failed deployment after merge
- Reopened PR or repeated change request
- Published-document readership or reuse, where applicable

Do not add revision or reversion counts merely because they are available. Their relevance is the delay or production impact they create, which should first be evaluated through time to close, release cadence, failed releases, or incidents. Do not infer quality from lines changed, comment volume, or review duration alone.

## Recommended implementation sequence

### Phase 1: Minimum viable attribution and flow

- [ ] Repository allowlist
- [ ] `AGENTS.md` labeling instructions
- [ ] Standard labels
- [ ] Primary type labels
- [ ] Generated metrics issues discovered and parsed across repositories
- [ ] Batched GitHub classification enrichment
- [ ] Fallback evidence fetched only for incomplete PRs
- [ ] Issue-listed PR allowlist with point-in-time metrics and separate current-outcome context
- [ ] Weekly `.rc` and full-release lookup

### Phase 2: Team context and release trends

- [ ] Bot identity registries
- [ ] Work classification
- [ ] Repository and team ownership mapping
- [ ] Development and production release-frequency trends
- [ ] Optional `.rc`-to-full-release promotion timing

### Phase 3: Quality outcomes when justified

- [ ] Failed-release and incident signals
- [ ] Documentation publication and adoption signals
- [ ] Trend reporting with cohort-size and attribution-coverage thresholds

## Initial scorecard

Once Phase 1 is complete, report these measures for AI-assisted, explicitly non-AI, and unknown-attribution cohorts:

- Merged PR count within the issue-listed cohort
- Share of merged, issue-listed PRs with confirmed or probable AI attribution
- PR count by primary work type
- Median and 90th-percentile time to first response
- Median and 90th-percentile time to close
- Closed-without-merge count
- Open and draft counts for the intake cohort
- Development (`.rc`) release count and frequency
- Production release count and frequency
- Attribution coverage and confidence mix

Always show the cohort size, reporting period, repository scope, and metric definitions with the scorecard.
