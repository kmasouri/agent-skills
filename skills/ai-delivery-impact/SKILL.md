# AI Delivery Impact

Build an evidence-backed view of work delivered with AI assistance. Treat AI activity as an input signal, not the outcome.

## Establish the question

Clarify the reporting period, teams, repositories or workspaces, and intended audience. Identify whether the user needs a one-time analysis, a recurring scorecard, or a proposed measurement system.

Ask for or inspect the available evidence. Prefer existing connectors, APIs, exports, or local files for systems such as source control, CI/CD, documentation, issue tracking, and AI-tool telemetry. Do not initiate browser login flows when an integration is missing. State gaps instead of inventing joins.

## Use generated issues and batched GitHub enrichment

Before reading PR timelines or calculating response and close durations, discover whether the scoped repositories already publish those metrics. Treat organization-generated metric records as the canonical source for every field they contain. For the current Compass implementation, search for GitHub issues titled `Weekly PR metrics report (YYYY-MM-DD..YYYY-MM-DD)` and use the row-level values generated by `github-community-projects/issue-metrics`.

Enrich only the PRs listed as rows in the selected weekly metrics issues. Treat the union of those PR URLs as an exact lookup allowlist. Use batched GraphQL or equivalent list queries to obtain lightweight fields for that cohort: PR number, labels, author, branch, current state, creation/close/merge timestamps, and URL. Do not run a separate repository-wide PR, merged-PR, author, or branch search. Query GitHub Releases independently for release cadence; releases are not PR lookups. Do not require an external analytics store.

Use a shallow-first lookup. Classify PRs with complete standardized labels without fetching descriptions, commits, contributors, reviews, or timelines. Fetch deeper evidence only for unlabeled, incomplete, or conflicting PRs. Do not independently recalculate an existing generated metric merely because raw events are accessible.

Respect the source's reporting grain:

- Use per-PR rows to aggregate across weeks; never average weekly medians or percentiles.
- Deduplicate rows by repository and PR number.
- Preserve generated durations when present. If a PR was open in the generated snapshot and later closed, calculate the missing duration from GitHub `createdAt` and `closedAt`, mark it `github-backfilled`, and retain the original missing source value.
- Prefer completed weekly windows. If the current partial week has no generated report, show it as pending rather than silently switching sources.
- Report current merged, closed-without-merge, open, and draft states only for the issue-listed PR cohort. Do not present that subset as every PR merged during the period.

Every result must include a source ledger naming the generated issues used for each metric, the covered dates, missing periods, the exact issue-listed PR lookup count, GitHub enrichment fields, and any `github-backfilled` values.

Keep the analysis assistant-neutral. Support any coding agent, IDE assistant, chat assistant, or future tool that can provide evidence. An artifact may involve multiple assistants; preserve all supported providers instead of forcing one primary provider.

For field definitions, attribution rules, and the minimum normalized record, read [references/measurement-model.md](references/measurement-model.md).

When designing, auditing, or preparing the organization-wide data collection required before analysis, read [references/implementation-prerequisites.md](references/implementation-prerequisites.md).

## Measure delivered work

Use lifecycle outcomes as the primary units:

- Code: merged pull requests or changesets; connect them to deployments when evidence exists.
- Deployments: successful releases containing attributable changes, with rollback or incident signals when available.
- Documentation: reviewed or published documents, runbooks, design records, or material updates—not drafts or prompt volume.
- Other artifacts: tests, automations, analyses, or specifications only when they are accepted into a team workflow and have durable evidence.

Show the delivery funnel where possible: created → reviewed → accepted/merged → deployed/published → adopted or reused. Deduplicate artifacts that appear in multiple systems.

Use volume only with balancing measures such as review latency, rework, reversions, defects, incidents, approval state, adoption, or reuse. Lines of code, prompts, active days, suggestion counts, and time in a tool may provide context but are never delivery outcomes by themselves.

## Attribute AI assistance carefully

Classify artifacts as confirmed, probable, possible, or unknown based on the evidence rules in the reference. Preserve the evidence source and confidence for every attributed artifact.

Use a canonical provenance record that is independent of provider-specific usernames, branch formats, or telemetry. Map provider-specific signals into that record. Treat branch prefixes and bot accounts as detectors, not as the schema itself.

Resolve PR attribution in evidence order. Use standardized PR labels first. Only when labels are absent or incomplete, inspect explicit declarations in the PR description, verified assistant or bot identities among contributors, task links or commit trailers, controlled branch-name conventions, and finally explicit title text. Record which fallback produced the inference and lower confidence as the evidence becomes less direct.

Do not infer AI use solely from writing style, commit shape, author identity, or a team-level license. Treat aggregate activity metrics as contextual signals only; map underlying evidence to artifacts when possible and report unmatched activity separately.

When comparing AI-assisted and other work, control or segment for team, work type, repository, and time period when the data supports it. Describe observed associations, not causal productivity gains, unless the study design supports causality.

## Report the result

Lead with a compact scorecard rather than a single composite score:

1. Delivery: accepted artifacts and the share that reached production or publication.
2. Flow: cycle time and review time, preferably medians and distributions.
3. Quality: rework, reversions, incidents, defects, or approval outcomes.
4. Adoption: reuse, readership, downstream references, or repeat usage where measurable.
5. Attribution quality: coverage, confidence mix, unmatched AI activity, and missing data.

Include methodology, scope, exclusions, and known blind spots. Break down by team or work type only when cohort sizes protect privacy and comparisons are meaningful. Never create individual leaderboards or use the analysis as a performance rating.

List metric provenance in the report. Distinguish organization-generated values from direct GitHub enrichment and independently calculated fallbacks so a reader can reproduce the result.

Recommend instrumenting missing joins—such as PR-to-deployment or AI-session-to-artifact identifiers—before recommending more telemetry. Keep collection proportional and avoid storing prompt contents unless the user explicitly needs them and has appropriate authority.
